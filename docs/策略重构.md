# 策略重构：OCR 与自动记账

版本 2.0 提案 · 2026-11-12 · 配套《现状诊断.md》

---

## 零、一句话结论

现在的架构是**「把有结构的信息压平成文本，再用字符串规则去猜」**。

压平这一步是不可逆的——位置、对齐、分组、语义关系全丢了。之后无论加多少正则、多少模板、多少强弱标签，都是在**把已经丢掉的信息重新猜回来**。这才是识别率上不去的根因，不是 OCR 引擎不行，也不是规则不够多。

所以要改的不是「换更强的 OCR」，是三件事：

1. **接对数据源**——用 `NotificationListenerService` 替代无障碍通知事件
2. **保住结构**——从「文本流」升级为「版面图」，在结构上做锚点定位
3. **承认不确定**——低置信度进「待确认队列」，而不是直接丢弃

---

## 一、自动记账策略

### 1.1 数据源重排：谁当主力，谁当兜底

现在是三条通道平行，谁先抓到谁记，没有优先级。改为**分级递进**：

```
第 0 级  NotificationListenerService（新增·主力）
         ├─ 优点：完整 Notification 对象、BIG_TEXT 全文、通知历史、MIUI 稳定
         ├─ 覆盖：所有装了支付/银行/电商 App 的通知
         ├─ 短板：微信支付通知本身不含商户名（产品设计，无解）
         └─ 定位：负责「抓到这笔交易存在 + 金额 + 渠道」

第 1 级  无障碍屏幕结构（改造·补商户）
         ├─ 优点：能拿到商户名、完整订单页信息
         ├─ 短板：依赖 App 前台、版式各异
         └─ 定位：负责「补第 0 级拿不到的商户名」

第 2 级  截图 + OCR（新增·兜底）
         ├─ 优点：版式无关，能对付小众 App / 小程序 / 网页
         ├─ 短板：需 MediaProjection 授权、耗电、隐私敏感
         └─ 定位：只在前两级都失败、且用户主动触发时用

第 3 级  手动补录（已有）
         └─ 定位：一切自动手段都失败时的最终出口
```

**关键改动**：第 0 级和第 1 级是**互补**而非竞争。同一次支付，通知给金额、屏幕给商户，两者用 `(方向, 金额, 时间窗)` 合并成一条完整账单——这个 `findSimilar` 机制已经有了，只是现在没有真正的第 0 级在喂数据。

### 1.2 白名单：从硬编码改为动态发现

现在是 12 个硬编码包名，用户装了新 App 就得改代码发版。而且这台设备上 5 个模板里 2 个（淘宝、京东）对应的 App 根本没装——写了永远触发不到。

改为**两级判定**：

```
第一级：这个包的通知值不值得看？
        → 不判断包名，判断「通知内容里有没有支付语义」
        → 关键词表：支付/付款/消费/扣款/交易/到账/入账/退款/实付/订单
        → 命中即进入第二级

第二级：内容是哪个 App 的什么版式？
        → 用现有 OcrTemplates 的「指纹」机制（markers / uniqueMarkers）
        → 命中 >= 2 普通标记 或 1 独特标记 → 高置信度
        → 未命中 → 走通用规则，置信度打折
```

这样：

- 用户装任何新 App 都能自动适配，不需要发版
- 已知的 5 个 App 享有高置信度快车道
- 未知 App 走通用规则 + 待确认队列，不会污染账本

**必须同步加的护栏**（防止变成「什么通知都记」）：

- 包名黑名单：系统 UI、输入法、安全中心、系统更新、运营商
- 通知标题/正文里出现「验证码/登录/广告/优惠券领取」→ 直接排除
- 金额为 0 或超过 100 万 → 排除
- 同一 App 在同一分钟内 > 5 条 → 判定为推送洪流，忽略

### 1.3 结构保留：屏幕采集不再压平

现在 `collectText` 递归把所有文本拼成一个字符串，位置信息全丢。

改为保留节点树：

```java
class ScreenNode {
    String text;
    Rect bounds;          // ← 关键：位置
    String viewId;        // ← 一些 App 会给稳定 ID
    int depth;
}
```

然后**锚点定位**，而不是正则扫：

```
步骤 1：找到金额锚点
        → 有强标签（实付/合计/付款金额）的行
        → 得到 anchorLine 的 y 坐标和 x 坐标

步骤 2：商户定位用三种结构关系，按可靠性排序
        a) 同行左侧：|y 差| < 行高，x 在锚点左边 → 最可能是商户
        b) 标签行下一行：标签在锚点上方，值是独立一行
        c) 页面顶部区域：dy < 40% 屏幕高 的纯文字节点

步骤 3：每个候选都打分，只有分数够高才采信
        → 打分维度：字号、位置、是否含数字、是否在噪声表里
```

这比正则多的好处：**不需要知道「商户」这个词长什么样**。哪怕 App 把标签写成「收款商家」「商户名称」「交易对方」，只要是「金额左边 / 标签下方」，结构上就能定位。

### 1.4 低置信度不丢弃，进「待确认队列」

这是当前设计里最该改的一点。

现在的规则是：

```java
if (r.confidence < 50) {
    Log.i(TAG, "✗ 丢弃 ...");
    return;                     // ← 直接扔掉
}
```

「宁可不记，不可错记」的**精神**是对的，但**实现**错了。「不记」的代价是用户完全不知道漏了什么——这恰恰是「自动记账效果差」的主观感受来源之一。

改成三档：

| 置信度 | 处理 | 用户看到 |
|---|---|---|
| >= 80 | 直接入账 | 顶部横幅「已记账 ¥39.20 华莱士」 |
| 50 ~ 79 | 入账但标记「待确认」 | 横幅「已记账（待确认）¥39.20」，账本里浅色底 |
| < 50 | **进待确认队列，不入账** | 通知「发现一笔疑似交易，点此确认」 |

待确认队列的价值：

- 用户不会「完全不知道漏了」
- 一键确认/修正，比手动补录快得多
- 修正数据可以本地统计（哪个 App 老出错 → 提示用户那个 App 用截图识别）

**账本永远只有用户确认过的账**，这一点不变；变的只是「不确定的东西有个地方放」，不再人间蒸发。

## 二、OCR 策略

### 2.1 从「文本流」升级为「版面图」

ML Kit 已经给了 `BoundingBox`，现在只用它排了个序就扔了。改为构建二维版面结构：

```
原始：TextBlock → Line（自带 bbox）
                          ↓
这一步现在做到了：按 y 排序、y-band 同行聚类、x 排序
                          ↓
这一步没做（该补）：把行还原成「表格」
    - 按 x 坐标聚类出「列」（左列=标签，右列=金额）
    - 同一 y-band 的多个 cell 合并成「一行记录」
    - 输出：List<Row>{ cells: List<Cell{text, left, right}> }
```

有了这个结构，「实付 | 39.20」就是一个 Row 的两个 Cell，**直接就是键值对**，不需要猜。

### 2.2 模板从「字符串匹配」改为「锚点 + 结构规则」

现在是：

```java
"实付".equals(line) → 取下一行
```

改为：

```java
// 1. 在 Row 结构里找强金额锚点（不看文本，看结构）
Anchor a = findAnchor(rows, STRONG_LABELS);
//   找到 Row{ cells:["实付", "39.20"] }，锚点 = cells[1]

// 2. 商户 = 锚点行的「语义邻居」
//    不需要知道标签叫什么，靠结构
merchant = nearestTextCell(rows, a, Direction.UP, maxDistance: 3 rows);
```

**收益**：能对付没见过的版式。「收款商家」「交易对方」「商户全称」甚至完全没有标签——只要位置关系稳定，就能定位。

### 2.3 多候选：从「全图扫金额」改为「结构化候选」

现在 `parseAll` 是把全文里所有金额都列出来——这会产生大量噪声候选（优惠前、优惠后、手续费、积分）。

改为**按结构生成候选**：

```
候选 1：强锚点行（实付 39.20）              ← 最可信
候选 2：强锚点行的「上方/下方」邻近金额
候选 3：出现次数最多的金额（账单页里总额常重复两次）
候选 4：带 ¥/元 且在页面下半部分的金额
```

每个候选都带上「为什么是它」的说明，让用户在对话框里能判断，而不是看一堆光秃秃的数字。

### 2.4 异体字归一：从「穷举映射」改为「模糊匹配」

现在建了个 `CONFUSABLES` 表（額→额、戶→户、颉→额…），只能覆盖见过的。真机上还会出现没见过的。

改为两层：

1. **保留映射表**（高频字，零成本，先命中）
2. **标签模糊匹配**：比较时用「编辑距离 <= 1 且长度相同」的近似匹配

```java
boolean labelMatch(String line, String label) {
    if (line.contains(label)) return true;              // 精确
    if (Math.abs(line.length() - label.length()) > 1) return false;
    return editDistance(line, label) <= 1;              // 容一个字的错
}
```

「支付金颉」vs「支付金额」编辑距离 = 1 → 命中。**再也不怕没见过的异体字。**

## 三、接入大模型：会怎么样

这是重点问题，分三种接入方式说清楚。**先说一件事实**：这台设备是小米，无 Google 服务框架，所以 **Gemini Nano / AICore 路线直接排除**，不用考虑。

### 路线 A：云端 LLM API（DeepSeek / 通义 / Kimi 等）

**怎么做**：把 OCR 出来的文字（或直接传截图给多模态模型）丢给 LLM，让它返回结构化 JSON：

```json
{"amount": 39.20, "merchant": "华莱士炸鸡汉堡", "type": "expense",
 "category": "餐饮", "confidence": "high"}
```

**效果预期**：这是三条路线里**准确率最高**的，而且**能解决规则完全解决不了的问题**：

| 场景 | 当前规则 | LLM |
|---|---|---|
| 标准账单页 | ✓ 已能处理 | ✓ |
| 从未见过的版式 | ✗ | ✓ 自己读语义 |
| 「优惠 8 元，实付 39.20」哪个是金额 | 靠强标签，勉强 | ✓ 理解「实付」是最终支付 |
| 「基金申购 99.92，手续费 0.10」主体是哪个 | ✗ 抓错（实测） | ✓ 知道主体是申购 |
| 截图里混了系统通知（如那条 #66） | ✗ 记成「通知栏 99.92」 | ✓ 自己分辨哪部分是交易 |
| 商户名带门店后缀、订单号、时间混在一起 | 正则截断，易错 | ✓ 语义抽取 |

**代价**：

| 维度 | 情况 |
|---|---|
| 钱 | 极低。一次抽取输入约 500 token，输出约 50 token，按 DeepSeek 定价算**约 0.0001 元/次**。一天 30 笔 = 每月不到 1 分钱（含重试也不到 1 毛） |
| 延迟 | 300 ms ~ 2 s（网络 + 推理），记账场景完全可接受 |
| 隐私 | **冲突点**。要把你的消费记录发到第三方服务器 |
| 稳定性 | 依赖网络；断网、限流、服务变更都会影响 |
| 可解释性 | 弱。错了不好查原因，只能重问 |

**这条路线和你之前定的「数据不出本机」原则直接冲突。** 这是必须你来拍板的取舍，我不替你决定。

### 路线 B：端侧小模型（1.5B ~ 3B，llama.cpp / MediaPipe）

**怎么做**：App 里塞一个量化模型（约 1~2 GB），本地推理。

**效果预期**：**明显低于云端，且未必强于规则。**

原因是端侧小模型的能力边界：

- 中文票据字段抽取这类任务，1.5B 模型**容易编造**（幻觉）——它会给你一个格式完美但金额错误的 JSON，比规则错得更隐蔽
- 不做专门微调的话，「39.20 是实付还是小计」这类判断经常错
- 要真正好用，需要**自己标注上千条真实账单微调**——这是另一个工程

**代价**：

| 维度 | 情况 |
|---|---|
| 钱 | 0 |
| 延迟 | 1~5 s（取决于机型），耗电明显 |
| 隐私 | ✓ 完美，数据不出设备 |
| 体积 | APK 从 45 MB 涨到 **1.5 GB+** |
| 内存 | 常驻 1~2 GB，小米可能直接杀后台 |
| 工程 | 大。模型打包、量化、推理引擎、机型适配 |

**结论**：端侧 LLM 现在**不值得作为主路径**。收益不确定，代价巨大。

### 路线 C：混合（推荐）

**核心思想：让 LLM 只做规则做不了的那一小部分。**

```
第 1 步  本地规则/模板（0 ms，0 成本）
         命中且置信度 >= 80 → 直接用，结束
                   ↓ 不确定
第 2 步  本地结构分析（版面图锚点定位，几十 ms）
         能定出金额+商户 → 用
                   ↓ 还是不确定
第 3 步  【可选·用户开启】云端 LLM 兜底
         只有这一步才联网
                   ↓ 网络不可用或用户关闭
第 4 步  进待确认队列，等用户一键确认
```

**为什么这是最优点**：

| 指标 | 纯规则 | 纯云端 LLM | 混合 |
|---|---|---|---|
| 常见账单准确率 | 高 | 最高 | 最高（走规则，同款） |
| 罕见版式准确率 | 低 | 高 | **高**（走 LLM） |
| 隐私 | ✓ 全本地 | ✗ 全上传 | **✓ 90%+ 不上传** |
| 成本 | 0 | 每月几毛 | **几乎为 0**（只有疑难才调） |
| 断网可用 | ✓ | ✗ | **✓**（降级到规则） |
| 延迟 | 快 | 慢 | **绝大多数快** |

**关键设计**：

- 兜底**默认关闭**，在设置里明确写「开启后，无法识别的账单会发送到 XX 服务解析」
- 每次调用**前**把将要发送的内容完整展示给用户（哪几个字），确认后才发
- 用户可随时关闭，关闭后退回「待确认队列」
- 只发 OCR 文本，**不发截图**（截图可能含余额、头像、其他隐私）
- 不留存、不记录请求

### 大模型解决不了什么

必须说清楚，避免预期过高：

- **拿不到数据的问题**（微信支付通知里就没有商户名）→ LLM 也变不出来
- **服务被杀** → 这是系统策略问题，与模型无关
- **需要授权的操作** → 拍照、截屏、装 App，模型帮不上

而且**它不能替代「待确认队列」**。任何自动系统都会错，把不确定的东西摆到用户面前让他一键确认，才是根本上解决「效果差」的办法。

## 四、落地顺序（按投入产出比排序）

| 优先级 | 改动 | 预期收益 | 工作量 |
|---|---|---|---|
| **P0** | `NotificationListenerService` 接入 | **最大**。数据源从「残缺」变「完整」，自动记账从「几乎不工作」变「可用」 | 中 |
| **P0** | 待确认队列（低置信度不丢弃） | 大。用户能看见漏了什么，「效果差」的主观感受直接改善 | 中 |
| **P1** | 版面图 + 结构锚点定位 | 大。OCR 从「猜」变「看」，罕见版式也能处理 | 中大 |
| **P1** | 白名单改为动态发现 | 中。装新 App 就能用，不用等我发版 | 小 |
| **P2** | 大模型兜底（可选开关） | 中。覆盖规则死角的疑难杂症 | 中 |
| **P2** | 标签模糊匹配 | 小但便宜。异体字不再怕 | 小 |
| **P3** | 截图 OCR 接入自动链路 | 低。代价大（录屏权限+耗电），收益有限 | 大 |

**建议先做两个 P0。** 这两个做完，「自动记账效果差」会有质变——因为现在的差主要不是解析不准，是根本没接对数据源、且不确定的东西被静默丢弃了。

## 五、需要你决策的事

1. **云端 LLM 兜底是否接受？** 这是隐私与准确率的取舍，你之前定的是「数据不出本机」。如果坚持全本地，方案里就去掉路线 C 的第 3 步，靠结构分析 + 待确认队列也能达到不错的效果，只是罕见版式仍需用户手动确认。

2. **截图 OCR 要不要接进自动链路？** 需要申请录屏权限（用户会有顾虑），耗电增加。我倾向不接，用通知 + 屏幕结构覆盖 95%，剩下 5% 走手动。

3. **先做哪两个 P0？** 还是按我建议的顺序，两个一起做？
