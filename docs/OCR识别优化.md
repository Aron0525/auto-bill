# OCR 识别准确率优化说明

> 目标：解决「小数点是重灾区」「商户认不出」两个最痛的问题。

---

## 一、为什么原来的准确率低

原来的 OCR 链路是这样的：

```
图片 → ML Kit → result.getText()（一大段纯文本）→ BillParser.parseAll()
```

问题出在**中间那一步**：`getText()` 把 ML Kit 识别出的「行」结构彻底压平了。而 ML Kit 本身其实是给了行和包围盒的，是我们自己丢掉了。

压平之后有两个致命后果：

### 1. 金额归属丢失（多金额场景必错）

一张外卖订单截图长这样：

```
华莱士
香辣鸡腿堡 x1        12.90
配送费               3.00
商品小计            15.90
实付                48.20      ← 这才是本笔金额
```

压成一段后，`12.90 / 3.00 / 15.90 / 48.20` 全掉进同一个池子，解析器只能靠关键词猜。猜错的概率很高——原来的 `extractAmount` 按 `P_PREFIX → P_CURRENCY → P_UNIT → P_NEG` 顺序找第一个命中的，「香辣鸡腿堡 x1 12.90」里的 12.90 会先被抓住。

### 2. 商户归属丢失

同理，压平后无法知道「哪个词和金额在同一行」。原来的 `detectMerchant` 只能靠「向 X 转账」「订单 X」这类句式模板，对「店名在最上面、金额在下面」这种最常见的电商/外卖版式几乎无效。

### 3. 小数点被吞

这是**训练数据层面的固有弱点**，不是正则的问题。ML Kit 对小字符（小数点、逗号、冒号）的召回率明显低于汉字和数字。实测三种典型错法：

| 正确 | 识别结果 | 原因 |
|---|---|---|
| `99.92` | `9992` | 小数点被完全吞掉，数字粘连 |
| `99.92` | `99,92` | 小数点被认成逗号 |
| `99.92` | `99 . 92` | 小数点前后被拆成两段 |

压成一坨文本后，`9992` 到底是多少钱无从判断。

## 二、做了哪些优化

### 优化 1：保留行结构（最重要）

`OcrHelper` 不再只返回 `getText()`，而是遍历 `TextBlock → Line`，把每行的文字和包围盒都留下：

```java
public static class OcrLine {
    public final String text;
    public final int top, bottom, left, right;
}
```

新增 `BillParser.parseOcr(List<String> lines, platform)`，按行归属：

- **金额**：给每行打分，`实付/合计/总计/支付金额` = 100 分，`小计/配送费/优惠/折扣` = 20 分，普通「文字 + 金额」行 = 60 分。取最高分的行。
- **商户**：优先取金额行里剥离金额后的文字；如果剥出来是 `实付` 这种标签词，就往上找最近一行「不含金额的纯文字行」——店名几乎总是不带钱的。
- **明细行整行跳过**：含 `配送费/打包费/小计/优惠` 等词的行不可能是店名。

这一条修好了「取错金额」和「商户认不出」两个问题。

### 优化 2：小数点修复（`fixOcrAmount`）

针对上面三种错法，用四条规则兜底：

```java
// (1) 金额前缀词 + 纯整数 + 元/¥/行尾 → 末两位是分
//     「实付 9992 元」→「实付 99.92 元」
// (1b) 「¥9992」→「¥99.92」（有 ¥ 就是明确的钱，长度 ≥4 才处理）
// (2) 逗号后正好 1~2 位 → 视为小数点
//     「99,92」→「99.92」（但不碰 1,280.00 这种千分位）
// (3) 小数点两侧被空格拆开 → 拼接
//     「99 . 92」→「99.92」
```

**关键约束**：只在「明确是金额的位置」修复。没有任何前缀词、没有 `¥`、没有「元」的纯数字一律不动——否则会把订单号 `202611061234` 补成 `2026110612.34`，那是灾难。

> 顺带修了一个真 bug：`P_PREFIX` 原来的间隔匹配是 `[^0-9¥\-]{0,8}`（最多 8 个非数字字符）。但 OCR 的多列对齐会用大量空格补位，实测「实付」到「99.92」之间有 16 个空格，**直接超出上限导致匹配失败**。已放宽到 `{0,30}` 并排除换行。

### 优化 3：图像预处理 + 二次识别

`OcrHelper` 增加两个预处理：

1. **放大**：短边不足 1200px 时放大到 1200px（上限 2 倍、4000px）。小数点只有 1~2 px 高，放大后 ML Kit 更容易分辨。
2. **对比度增强**：灰度 + 对比度 1.45 倍。注意**不用纯二值化**——黑白二值会把抗锯齿的小点直接抹掉，反而更糟。

策略是**两遍识别 + 打分取优**：

```
第一遍（放大图）→ 如果结果里一个带小数的金额都没有
                → 第二遍（放大 + 增强图）
                → 按「带小数的金额个数 + 行数」打分，取分高的
```

只在第一遍「可疑」时才跑第二遍，正常图片不会多等一次。

### 优化 4：置信度折减

OCR 天生比通知栏不可靠（受截图质量、字体、缩放影响），所以 `parseOcr` 里置信度整体 ×85%。这是遵循项目既定原则「宁可不记，不可错记」——置信度低于 50 会被已有逻辑丢弃。

## 三、一个容易踩的坑：「收款」的歧义

测试时发现加「收款」到收入词列表会导致回归：

| 文本 | 正确方向 | 只看「收款」的后果 |
|---|---|---|
| `收款 250.00 元` | 收入 | ✅ |
| `你已成功支付 ¥36.00 收款方：华莱士` | **支出** | ❌ 被判成收入 |

「收款方」只是商户的标签，不是「我收到钱」。所以改成带否定的正则：

```java
Pattern.compile("收款(?!方|人|账户|账号|卡号|码|单位|名称)")
```

这个坑值得单独记下来——**中文支付文案里同一个词根常常表达相反方向**，类似还有「退款」（收入）vs「退款申请已提交」（不是交易）。

## 五、还能继续提升的方向

按性价比排序：

| 手段 | 效果 | 代价 |
|---|---|---|
| **截图前让用户裁剪** | 去掉无关区域，多金额干扰直接消失 | 需要交互，但对准确率提升最直接 |
| 针对特定 App 的版式模板 | 美团/饿了么/淘宝各自写一套行定位规则 | 维护成本高，但准确率能做到接近 100% |
| 用 `OcrLine` 的包围盒做空间聚类 | 利用「金额右对齐」这一特征筛选候选 | 中等，需要处理不同分辨率 |
| 多帧投票（同一页连拍两张） | 抵消单次识别的随机错误 | 需要用户配合，体验变重 |
| 换更强的 OCR 模型 | 小数点召回率本质提升 | 模型体积大 / 可能要联网，违背「纯本地」 |
| 用户纠正后学习 | 记住「这家店上次的商户名」 | 需要积累数据 |

其中**包围盒空间聚类**是最值得做的下一步：账单类截图里金额几乎总是右对齐，用 `right` 坐标聚类就能把「价格列」和「文字列」分开，比现在的关键词打分更稳。

## 六、给用户的使用建议

1. **截图时只截账单区域**，别把整个屏幕都截进去——干扰越少越准。
2. 识别出多个候选时，勾选框里会显示每个候选的金额/商户，**选对的那个**，不要全选。
3. 金额识别错了，直接点开账单用「编辑」改——比重新识别快。
4. 如果某类截图（比如某家银行 App 的流水页）总是不准，把截图发我，我针对那个版式加规则。

## 五、版本 1.6：特定 App 版式模板

### 为什么加模板

前四节的规则都是「通用启发式」：靠金额标签词 + 上下文猜。在这些版式固定的 App 里，
这属于舍近求远 —— 每个 App 的钱放在哪、商户叫什么，都是稳定的。直接按版式定位，
准确率可以逼近 100%。

### 覆盖的 5 个 App

| App | 强金额标签 | 商户来源 | 商户方向 |
|---|---|---|---|
| 微信支付 | 支付金额 / 转账金额 / 支付成功 | 商户全称、收款方、付款给 | 金额**下方** |
| 支付宝 | 支付金额 / 实际支付 / 交易成功 | 商户全称、收款方 | 金额下方 |
| 美团外卖 | 实付款 / 实付 / 在线支付 | 店名（金额上方纯文字行） | 金额上方 |
| 饿了么 | 实付金额 / 实付 / 已支付 | 店名 | 金额上方 |
| 淘宝/天猫 | 实付款 / 实付 / 应付 | 店铺 | 金额上方 |

### 设计要点

**1) 模板只增强，不替代**

```
parseOcr()
  ├─ 模板命中且取到金额 → 用模板结果
  └─ 否则             → 落到原来的通用规则
```

新增模板绝不会让原本能识别的截图变差。自检里专门有一条「无 App 特征的普通小票」
必须仍走通用规则并通过。

**2) 版式指纹防误判**

「聊天里提到美团」不能被当成美团订单页，所以判定门槛是：

- 命中 >= 2 个普通版式词（配送费 / 商品小计 / 待评价 …）→ 认
- 命中 1 个普通版式词 + App 名 → 认
- 只命中 App 名（美团外卖 / 淘宝 / 支付宝）→ **不认**
- 只命中 1 个普通版式词 → **不认**

**3) 标签按长度降序匹配**

「商户全称 华莱士」如果用「商户」去 indexOf，会剥成「全称 华莱士」。
所有商户标签先按长度降序排序，保证「商户全称」先于「商户」被匹配。

**4) 跨行取值**

支付宝的版式是：

```
支付金额
56.80
```

标签和金额分两行。所以模板金额扫描支持「强标签独占一行 → 看下一行」。

**5) 裸小数**

OCR 出来后 `¥36.50` 常被拆成单独一行 `36.50`。原来的 `extractAmount`
要求必须带 ¥ / 元 / 前缀词，这类全漏。新增 `extractOcrAmount()`：

- 先走通用规则
- 再试「整行只有一个带 1~2 位小数的数字」（纯整数不认，可能是数量/序号/页码）

### 验证结果

| 套件 | 结果 |
|---|---|
| 版式模板自检 | 31 / 31 |
| 真实版式端到端（三张测试图的行序列） | 11 / 11 |
| 原有解析自检 | 49 / 49 |
| OCR 优化自检 | 19 / 19 |
| 通知切割自检 | 5 / 5 |
| 多候选自检 | 7 / 7 |
| **合计** | **122 / 122** |

真实版式端到端用例里，美团那张图有 7 个干扰金额
（12.90 / 25.80 / 8.50 / 4.00 / 2.00 / 47.20 / -8.00），
必须精准取到 **39.20** —— 这一条通过，说明模板行定位确实生效。

### 局限性

1. App 改版会让模板失效 —— 但因为有「不命中退回通用规则」兜底，失效不会变糟，只是退回原来的准确率。
2. 目前只覆盖「账单详情页」。列表页（如支付宝账单列表多条目）仍走 `parseAll` 多候选。
3. 商户名截断在 16 字，「华莱士炸鸡汉堡（科技园店）」正好卡在边界。如果实测发现长店名被截，把上限提到 24。
