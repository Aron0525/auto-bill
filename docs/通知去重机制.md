# 通知去重机制说明

> 目标：同一条支付通知，无论被系统投递多少次、被几条通道抓到，账本里都只记一笔。

---

## 一、为什么会重复读同一条消息

Android 的通知事件不是「一条消息一次回调」，实际会遇到这些情况：

| # | 触发场景 | 现象 |
|---|---|---|
| 1 | 通知内容更新（如「支付中」→「支付成功」） | 同一条通知多次回调 |
| 2 | 用户下拉/收起通知栏 | 每次展开都重新投递 |
| 3 | 亮屏、解锁、切换应用 | 通知被重新广播 |
| 4 | 用户点「展开」查看长文本 | 又一次回调 |
| 5 | 同一笔交易的多个来源（微信通知 + 微信页内 + 银行短信） | 文本完全不同，各来一次 |
| 6 | 无障碍服务被系统重启后重放 | 历史事件重新投递 |
| 7 | 支付页 `TYPE_WINDOW_CONTENT_CHANGED` 高频刷屏 | 同一屏文本几百毫秒一次 |

第 1–4 是「同一条消息重复读」，第 5 是「同一笔交易多来源」，两者要分开处理。

---

## 二、已实现的五层去重

按拦截成本从低到高排列，前面的挡住就省掉后面的开销。

### 第 1 层：通知身份键（内存）

```java
noteKey = pkg + ":" + notification.when + ":" + title
```

`Notification.when` 是发通知时的时间戳，同一条通知的多次投递它不变；一旦变成一条新通知，`when` 必然变。配上包名和标题，30 分钟内同键直接丢弃——**连解析都不做**。

解决场景 1、2、3、4、6。

### 第 2 层：正文指纹（内存）

```java
fp = pkg + "|" + raw.replaceAll("\\s+", "")
```

把通知正文压成一行后做指纹。挡住「同一条文字换了个 NotifID / 换了窗口再抓一次」的情况——典型是场景 7（支付页高频刷新）和场景 1（内容没变的重发）。

解决场景 7，兜住场景 1。

### 第 3 层：屏幕采集节流（800 ms）

`handleWindow()` 里 `lastScreenScan` 控制，同一时间窗只抓一次屏幕文本。`TYPE_WINDOW_CONTENT_CHANGED` 会以毫秒级频率触发，不节流会瞬间打满 CPU 并产生大量重复解析。

解决场景 7 的洪泛。

### 第 4 层：语义去重（查库，5 分钟窗口）

```sql
同 type + 同 amount_fen + 同 merchant，ts 在 [now-5min, now+1min]
```

这是**跨通道**的兜底。同一条微信支付，通知通道拿到的是 `"微信支付 你已成功支付￥25.00 收款方：华莱士"`，页面通道拿到的是 `"华莱士 支付成功 25.00"`——文本指纹完全不同（第 2 层拦不住），但「支出 + 2500 分 + 华莱士」在 5 分钟内一定重合。

命中时不新增，只做一件事：如果新来源置信度更高，就上调已有那笔的置信度（`bumpConfidence`）。

解决场景 5。这是最重要的一层。

### 第 5 层：数据库唯一索引（持久化）

```sql
dedup TEXT UNIQUE
dedupKey() = type | amountFen | hashCode(raw前60字)
```

`insertWithOnConflict(..., CONFLICT_IGNORE)`。即使前四层全漏了（比如服务重启丢了内存表、跨进程并发），数据库这层是硬约束，插不进去就是插不进去。

特别处理：手动记账的 `raw` 是固定字符串「手动记账」，如果也按内容做指纹，两笔同额手动账会被永远吞掉一笔。所以手动记账的指纹改用**分钟粒度时间**：

```java
return type + "|" + amountFen + "|manual|" + (ts / 60000L);
```

解决场景 6（服务重启后内存表清空），也是最后的正确性保证。

## 三、关于「读取消息的时间」能否避免重复

**能解决一部分，而且是最省事的一层，但不能只靠它。**

### 可用的时间信号

| 信号 | 含义 | 稳定性 |
|---|---|---|
| `Notification.when` | 通知创建时间戳 | 同一条通知的多次投递**不变**，非常适合做身份键 |
| `AccessibilityEvent.getEventTime()` | 事件投递时间 | 每次投递都变，**不能**用来判重 |
| `Notification.postTime` | 首次 post 时间 | 同 `when`，稳定 |
| 内容里的交易时间（`12:37`） | 银行/支付机构的入账时间 | 稳定，但格式五花八门，需解析 |
| `System.currentTimeMillis()` | 记账时刻 | 已用作 5 分钟窗口的时间基准 |

### 结论

1. **事件到达时间不可用于判重** —— `getEventTime()` 每次都不同，拿它做键等于没去重。
2. **`Notification.when` 可用且很有效** —— 这正是第 1 层的实现方式。它是「消息自身的身份」，不是「我们读到它的时刻」。
3. **时间窗口（5 分钟）是必要的补充** —— 处理跨来源、跨通道的情况，因为不同来源的 `when` 必然不同。
4. **窗口不能太宽** —— 5 分钟是我按支付场景定的：够覆盖「通知 + 页面 + 短信」的传播时间，又不至于把「同一家店连买两次相同金额」吞成一笔。若要更保守，可缩到 2 分钟；若要更激进防重，可放到 10 分钟，代价是连续同额消费可能漏记。

## 四、尚未实现、可按需加上的手段

| 手段 | 说明 | 代价 |
|---|---|---|
| 通知 Key 精确匹配 | 用 `Notification.getKey()`（API 20+）替代 `when+title`，唯一性更强 | 需要 API 20+，本项目 minSdk 23 满足 |
| 交易流水号提取 | 银行短信常带「交易号 20261106...」，用它做主键最准 | 需为每家银行写正则，维护成本高 |
| 内容哈希的 SimHash 去重 | 对文本做相似度匹配而非完全相同，抗文字微调 | 算法复杂度提升，本地实现较重 |
| 时间窗口自适应 | 同商户历史上重复次数多则放宽窗口 | 需要统计逻辑，收益有限 |
| 用户可见的「疑似重复」提示 | 不自动合并，让用户决定 | 增加交互负担，违背「不打扰」原则 |

## 五、验证方式

```bash
# 1. 触发一次记账，看日志里的去重标注
adb logcat -s AutoBill:* | grep -E "✔ 记账|· 重复|· 跳过"

# 2. 连发同一条通知三次，应该只有第一次记账
adb shell am broadcast -a com.aron.autobill.TEST_NOTIFY -p com.aron.autobill
adb shell am broadcast -a com.aron.autobill.TEST_NOTIFY -p com.aron.autobill
adb shell am broadcast -a com.aron.autobill.TEST_NOTIFY -p com.aron.autobill

# 3. 确认账本只多了一笔
adb shell run-as com.aron.autobill sqlite3 databases/autobill.db \
  "SELECT _id, amount_fen, merchant FROM bills ORDER BY _id DESC LIMIT 3;"
```

日志里的三种标记含义：

- `✔ 记账[...]` —— 新增成功
- `· 重复(语义)[...]` —— 第 4 层拦下（跨通道同一笔）
- `· 重复(指纹)[...]` —— 第 5 层拦下（内容完全一样）
- `· 跳过重复通知(身份)[...]` —— 第 1 层拦下（同一条通知重复投递）
- `· 跳过重复通知(指纹)[...]` —— 第 2 层拦下（同文本换 ID）
