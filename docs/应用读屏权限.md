# 应用读屏权限（浏览 vs 付款的区分）

> 解决的问题：**「刷一会拼多多全是账单」**
>
> 用户原话：「现在他无法分辨我是在浏览商品还是已经付款了，刷一会拼多多全是账单，
> 只有支付宝和微信两条链路是比较稳的。」

---

## 一、根因：不是解析错了，是数据源用错了

先说结论：**假账不是通知造成的，是无障碍读屏造成的。**

两条采集通道的性质完全不同：

| 通道 | 输入长什么样 | 可信度 |
|---|---|---|
| 通知 | 「支付成功 ¥36.50 收款方：瑞幸咖啡」 | 高 —— App 主动告诉你的**结论** |
| 读屏 | 「¥36.50 ¥9.9 ¥29.9 立即购买 加入购物车…」 | 低 —— 你从屏幕上**猜**的 |

读屏通道每 800ms 抓一次当前屏的全部可见文本。商品列表页一屏就有几十个价格，
滑动一下内容全变，又抓一次 —— 于是每滑一屏就产生一条假账单。

原来的代码对此毫无防备：`handleWindow` 抓完文本直接送进 `BillParser`。
解析器本身没错（它确实看到「¥29.90」），错的是**不该把这段文本给它**。

商品页的价格是「展示」，不是「交易」。这是数据源层面的语义错误，
再多解析规则也救不了。

---

## 二、三层防线

### ① 应用级开关（用户的最终裁决权）

设置 → 应用读屏权限 → 逐个 App 三档：

| 档位 | 含义 | 出厂默认给谁 |
|---|---|---|
| **信任** | 屏幕文字直接记账 | 微信、支付宝、银行、运营商 |
| **需凭证** | 必须看到「支付成功/实付款」才记账 | 电商、外卖、出行、团购 |
| **不读屏** | 完全不用这个 App 的屏幕文字 | 未收录的 App |

**为什么让用户来定**：每个人的习惯不同。只用支付宝付钱的人，
把所有购物 App 关掉读屏最省心；习惯在小程序里付款的人，就得留着。
这种偏好猜不出来，只能问。

改动立即生效，写入 `SharedPreferences`（键 `screen_lv_<包名>`），
「恢复默认」可一键清空全部自定义。

### ② 应用信任级别（出厂默认）

判据不是「这个 App 会不会花钱」，而是
**「它的屏幕上会不会出现大量与交易无关的金额」**：

- 微信/支付宝：付款结果页文字就是结账结论，几乎没有商品列表 → `TRUSTED`
- 电商/外卖/出行：满屏商品价、优惠价、划线价 → `CAUTIOUS`
- 银行/运营商：账单页文字是正式账单 → `TRUSTED`
- 其余：`OFF`，让通知通道去干活

### ③ 结账凭证门禁（`CAUTIOUS` 的核心）

`CAUTIOUS` **不是「不记账」**。用户真的下单付款了，这页文字会通过门禁：

```
支付成功 实付款 ¥36.50 支付方式 支付宝 订单编号 2411152200188
```

要求命中以下之一：

**成功动词**（交易已经发生）
```
支付成功 付款成功 交易成功 交易完成 支付完成 付款完成
已支付 已付款 扣款成功 付款给 支付给 支付金额
```

**结果页结构**（付款后才有的字段）+ 必须带金额
```
实付款 实付 支付方式 订单编号 订单号 交易单号
付款时间 支付时间 收款方 商户名称 已完成
```

单独一个「订单号」不算 —— 商品详情页也会显示订单号提示，所以要求「有金额」。
这条限制是被真实误判逼出来的。

## 三、商品浏览页识别

除了「要求凭证」，还主动识别浏览页。两个层次：

**铁证词**（单独出现即可判定）
```
加入购物车 立即购买 立即抢购 马上抢 去结算 购物车
```
这几个词在**结账成功页里不会出现** —— 付完款是「支付成功 实付款」，
没有购物车按钮。

**特征词**（累计 ≥3 个才判定）
```
店铺 商品详情 累计评价 已售 收藏 客服 领券 优惠券
限时秒杀 百亿补贴 拼单 全选 已拼 加购 搜同款 找相似
```

**顺序很重要**：先看结账成功凭证，再看浏览页特征。
因为付款完成页可能残留「店铺」等字样（比如「感谢光临 XX 店铺」），
有成功凭证时不该判成浏览页。

---

## 四、一个必须承认的设计取舍

`TRUSTED` 级别**仍然拦商品浏览页**。这不是配置问题，是正确性问题：

即使用户手动把拼多多设成「信任」，浏览商品页依然不记账。
理由是「信任」表达的是「这个 App 的付款页我信」，
不包括「它的商品列表页也是账」—— 后者是任何配置下都不成立的事实。

用户真想连浏览页都记，那是另一个功能（手动记录），不是自动记账。

## 五、真机验证

设备：Xiaomi 2312DRAABC / Android 14，装上 `com.taobao.idlefish`（闲鱼，出厂 `CAUTIOUS`）。

| 场景 | 日志/结果 | 账本 |
|---|---|---|
| 刷闲鱼商品页（滑动 5 次） | `不读屏[com.taobao.idlefish] 未看到结账凭证` | 3 → 3（未增加）|
| 注入闲鱼结账成功页文本 | 正常记账 | 3 → 4 |
| 注入「支付成功 实付款 88.00 支付方式 支付宝」 | `#36 闲鱼 ¥88.00 支出 [购物] conf=75 pending=1` | ✓ |

**关键证据**：

```
I AutoBill: · 不读屏[com.taobao.idlefish] 未看到结账凭证  返回 闲鱼 WVUCWebView
```

浏览页被拒，结账页放行，一次验证同时覆盖两个方向。

设置页交互也已验证：切换到「不读屏」后
`screen_lv_com.sankuai.meituan=2` 立即落盘，统计从「需凭证 23」
变为「需凭证 22 · 不读屏 1」，条目自动移到「不读屏」分组；
「恢复默认」后配置项被删除，统计回到「需凭证 23」。

## 七、与通知通道的关系

**互不影响。** 这是刻意设计的：

- 通知通道（`NotificationListenerService`）不受应用读屏开关影响，
  微信、支付宝的支付通知始终有效 —— 这也是用户说「比较稳」的那两条链路。
- 读屏只是一个**兜底补充**：小程序付款、银行 App 页面这类
  没有通知的场景才需要它。

所以最省心的配置是：**所有购物 App 设为「不读屏」**。
购物付款时支付宝/微信会发通知，那条链路准；商品页那些价钱一条也不进账本。
