## 一、修那 3 条商户规则

同一套 8 道题（与端侧小模型基准同一张考卷），修复前 5/8，修复后 **8/8**。

| 案例 | 修复前（错） | 修复后（对） | 病根 |
|---|---|---|---|
| 退款到账 | `名称` | **京东商城** | 「商户名称 京东商城」被当成整体，剥金额后剩「名称」 |
| 工资到账 | `短信` | **招商银行** | `【招商银行】您账户…` 整句超长被拒，退化到平台名 |
| 微信红包 | `微信` | **张小明** | `isLabelWord` 漏了「收款人」，取值失败退化到平台名 |

### 改了什么

`BillParser.java` 新增三层提取，接到 `parse()` 和 `parseOcr()` 两条路径的商户定位链：

```
投资品名 > 银行短信【…】前缀 > 「标签+值」> 金额行文字 > 上一行 > 平台名
```

1. **`MERCHANT_LABELS`**（按长度降序）
   `商户全称` / `商户名称` / `收款方` / `收款人` / `付款方` / `交易对方` / `户名` …
   降序是关键：否则 `indexOf("商户")` 先命中「商户全称 华莱士」，剥出「全称 华莱士」。

2. **`valueAfterLabel()`** — 取标签后的值，并在**下一个标签处截断**。
   不截断的话「京东商城 退款时间 2026-11-11」会把时间一起吞进商户名。

3. **`extractBankName()`** — 优先匹配 `【招商银行】` 这类方括号前缀。

4. **`isLabelWord()` 扩充** — `名称/商户/商家/收款方/摘要/备注/时间/单号/账户/短信/通知…`
   这些是**字段名**，永远不是值。

5. **`cleanItems()`** — 条目清洗。「支付方式 零钱」描述的是渠道不是商品，清空。

### 真机证据

```
✔ 记账[test] 收入 ¥36.50   京东商城  [退款] 置信度=70 (待确认)
✔ 记账[test] 收入 ¥12000.00 招商银行  [工资] 置信度=80
✔ 记账[test] 支出 ¥88.00   张小明    [红包] 置信度=90
```

主界面账单列表实拍：
```
红包   微信自动记账   17:28 | 张小明     -88
工资   短信          17:28 | 招商银行   +12000
退款   微信自动记账   17:28 | 京东商城   +36.50
```

回归：**208 条断言全绿**（Parser 49 / Candidate 7 / Notice 5 / Ocr 19 / Template 31 /
RealImage 11 / Update 45 / VisualSort 33 / 规则基线 8）。

## 二、接 NotificationListenerService

### 为什么这是质变

| 能力 | 无障碍通知事件 | NotificationListenerService |
|---|---|---|
| Notification 对象 | MIUI 上经常为 null | 总是有 |
| `EXTRA_BIG_TEXT` | 常被截断 | **完整全文** |
| 通知历史 | ✗ | ✓ `getActiveNotifications()` |
| 应用名/图标 | ✗ | ✓ |
| MIUI 稳定性 | 差（易被杀、丢事件） | 好 |
| 系统标准 API | 非本职 | ✓ 正是本职 |
| 审核风险 | 无障碍被严查 | 低 |

旧账本 66 条里唯一的 1 条真机记录来自「整屏通知栏」——正因为无障碍拿不到完整
`Notification`，只能退化去读屏。

### 实现

**`BillNotificationListener.java`（新）**
- `NotificationListenerService`，`onNotificationPosted` 全 try-catch 兜住
  （监听服务崩一次就再也收不到任何通知）
- 正文提取优先级：`EXTRA_TITLE` + **`EXTRA_BIG_TEXT`** > `EXTRA_TEXT`，
  再补 `EXTRA_TEXT_LINES` / `EXTRA_SUB_TEXT`
- 三道闸：包名过滤（跳过自己和系统 UI）→ 通知身份 `pkg:id:when` 30 分钟去重 → 支付语义预筛
- **不限包名**：靠内容判断而不是白名单，用户装任何新 App 都能自动适配，不必改代码发版

**`BillProcessor.java`（新）** — 通知通道与屏幕通道共用的落账核心。
抽出来的理由：去重、置信度分档、落库、提示必须完全一致，各写一遍迟早走偏。

**`TestPipeReceiver.java`（新）** — 端到端自检入口：
```bash
adb shell am broadcast -a com.aron.autobill.TEST_PIPE \
    --es text "微信支付 收款到账 ¥36.50 华莱士" \
    --es pkg com.tencent.mm -p com.aron.autobill
```
真机没法伪造「其他应用发来的通知」，而这套管道是整个 App 的价值所在，必须能单独验证。

### 真机证据

```

    ComponentInfo{com.aron.autobill/com.aron.autobill.BillNotificationListener} (user 0)
日志: I AutoBillNotif: 通知监听已连接，开始监听交易通知
```

授权命令（免手动点）：

> 必须用 `cmd notification allow_listener`（或撤销再授权）才会真正连上。

## 三、待确认队列

### 解决的是主观感受问题

旧逻辑对置信度 < 50 的解析结果**直接 `return` 丢弃**。
「宁可不记，不可错记」的精神没错，但用户完全不知道漏了什么——
这正是「自动记账效果差」的主观来源。

### 三级置信度分档

| 置信度 | 行为 | 用户感知 |
|---|---|---|
| ≥ 80 | 直接入账 | 顶部横幅「已记账」 |
| 50 ~ 79 | 入账 + `pending=1` 标记 | 顶部横幅「已记账（待确认）」 |
| < 50 | **进待确认队列，不入账** | 「发现一笔疑似交易，待确认」通知 + 角标 |

### 实现

- **`PendingStore.java`**（新）— 独立 `pending.db`，不污染账本
- **`PendingActivity.java`**（新）— 卡片列表，三个动作：
  - **确认** → 入账
  - **修正** → 改金额/商户/方向/分类后入账
  - **忽略** → 删除，不入账
- **`BillStore` v4→v5** — 加 `pending` 列，平滑迁移（老数据默认 0，不丢账）
- **设置页** — 待确认入口 + 数量角标 + 通知使用权状态引导

### 真机证据

设置页：
```
待确认交易              有 1 笔拿不准的交易等你确认     [1] ›
通知使用权（推荐开启）   已能读取完整通知正文…          已开启
```

队列页：
```
共 1 笔待确认
com.example.unknown                          -15.00
其他 · 置信度 45 · test
某笔交易 ¥15.00 未知
[确认]  [修正]  [忽略]
```

点确认后 → 队列清空显示空状态 → 主界面账本 **3 笔 → 4 笔**，
出现 `-15`，支出合计 88 → **103**。链路闭环。

## 四、端侧 1.5B（按要求放最后）

### 结论：现在不建议做，但不是因为硬件不够

之前实测时 `/data` 只剩 1.8 G，是硬伤。现在复查：

```
/data 可用 10 G
内存 7.7 G，可用 3.6 G
CPU 8 核（A76×2 @2.4GHz + A55×6）
```

**存储和内存都不再是阻碍**（Qwen2.5-1.5B Q4_K_M 约 1066 MB）。

### 真正的理由

1. **前三项已经把规则准确率拉到可用**
   8/8，且是同一个考卷。小模型 1.5B 在同一考卷上的成绩：金额 6/7、
   商户 6/7、方向 7/8（需中文枚举 + 1 个 few-shot）。**没有显著优势**。

2. **一次推理 ~2-4 秒**，而通知到达需要即时落账。体验上是倒退。

3. **1/8 的 JSON 解析失败率**（markdown 围栏、返回数组）。规则不会有这个问题。

4. **APK 会从 46 MB 涨到 1.1 GB**。远程更新每次要传 1 GB。

### 如果将来要做，正确姿势

- 规则**为主**，小模型**只在规则给出 < 50 置信度时兜底**——正好接在待确认队列前面
- 中文枚举 + 1 个 few-shot（这是实测把方向从 2/8 提到 7/8 的关键）
- `Q4_K_M` + `max_tokens=128` + 容错 JSON 解析（去 markdown 围栏）
- 模型文件**不进 APK**，首次启动时下载（避免 1 G 的更新包）

详见 `端侧小模型实测.md`。
