# 端侧小模型实测报告

实测日期：2026-11-12 · 结论基于真实数据和真实模型，非推测

---

## 一、结论先行

**接小模型可行，但只能当「兜底」，不能当主力。**

|\n| 方案 | 金额 | 商户 | 方向（优化后） | 综合 |
|---|---|---|---|---|
| **现有规则** | 7/8 | **5/8** | **8/8** | 最稳 |
| Qwen2.5-0.5B | 2/7 | 5/7 | 3/8 | **不可用** |
| Qwen2.5-1.5B | 6/7 | **6/7** | 7/8（prompt C） | 有竞争力 |

关键发现：

1. **0.5B 完全不能用**——金额 2/7，连基本的数字定位都做不对。端侧尺寸下，0.5B 是废的。
2. **1.5B 在「商户名」上明显强于规则**（6/7 vs 5/8）——这正是规则的死穴：规则靠「商户」「收款方」这类标签匹配，没有标签就抓瞎，而 LLM 能理解语义。
3. **规则在「金额」和「方向」上更可靠**——规则是确定性的，不会像 LLM 那样把「支出」判成「income」。
4. **prompt 措辞对 1.5B 影响巨大**：方向准确率从 38% → 88%，仅靠把 `expense/income` 换成 `支出/收入` 加一个 few-shot 示例。这说明端侧模型不是「不能做」，是「要精心伺候」。

**所以最优解不是「用 LLM 替代规则」，而是：规则跑主路径，1.5B 只在规则不确定时补位。**

## 二、实测数据

### 2.1 考卷（8 个案例，全部来自真实数据）

| 案例 | 来源 | 难点 |
|---|---|---|
| real_systemui | **真机账本 #66 原文** | 整屏通知栏，系统噪声 + 两个金额 |
| meituan | 真机 OCR 输出 | 7 个干扰金额 |
| wechat | 真机 OCR 输出 | 繁体「商戶」 |
| alipay | 真机 OCR 输出 | 异体字「金颉」+ 金额换行 |
| refund | 构造 | 退款方向易判错 |
| salary | 构造 | 银行短信格式 |
| redpacket | 构造 | 红包是支出不是收入 |
| multi | 构造 | 一条含两笔交易 |

### 2.2 规则基线（`LlmBenchBaselineSelftest`）

```
[PASS] real_systemui  真机#66 整屏通知栏
[PASS] meituan        美团订单页
[PASS] wechat         微信支付凭证
[PASS] alipay         支付宝账单详情
[FAIL] refund         退款到账        · 商户 期望⊇[京东]    实际=名称
[FAIL] salary         工资到账        · 商户 期望⊇[工资,招商] 实际=短信
[FAIL] redpacket      微信红包发出    · 商户 期望⊇[红包,张小明] 实际=微信
[PASS] multi          短信含两笔交易

==== 规则基线: 5 通过 / 3 失败 ====
金额 8/8 · 方向 8/8 · 商户 5/8
```

**规则的弱点非常集中：金额和方向几乎全对，商户名错 3 个，且错法都是「把标签或来源当商户」。** 这恰好是 LLM 的强项。

### 2.3 Qwen2.5-0.5B（469 MB，Q4_K_M）

```
金额   2/7      商户 5/7      方向 3/8      JSON 解析失败 1/8
```

典型失败：

- 美团页 7 个金额，它选了 **47.20（商品小计）**而不是 39.20（实付）
- 支付宝「支付金颉 56.80」→ 金额返回 `null`
- 红包 88.00 元 → 金额 `null`，方向 `income`
- 输出 JSON 出现**重复字段**（`"amount"` 出现两次），自己把自己写崩

**判定：0.5B 不可用。** 它的错误是「不知道该选哪个」，比规则错得更隐蔽。

### 2.4 Qwen2.5-1.5B（1066 MB，Q4_K_M）

原始 prompt（英文枚举）：

```
金额 6/7      商户 6/7      方向 2/8
```

方向几乎全判成 `income`——包括「微信支付 支付成功」「美团实付 39.20」。这不是不理解，是**英文标签 `expense`/`income` 在中文语境下的对齐很差**。

### 2.5 方向专项：4 种 prompt 对比

```
prompt A  英文枚举 expense/income           3/8  (38%)
prompt B  中文枚举 支出/收入                 6/8  (75%)
prompt C  中文枚举 + 1 个 few-shot 示例      7/8  (88%)  ← 最佳
prompt D  中文 + 要求输出 reason             5/8  (62%)
```

prompt C 唯一错的还是 `real_systemui`——那条整屏通知栏文本里同时有「入账」和「买入」，**人看了也要多看两眼**。这种该进待确认队列，而不是让模型硬猜。

**这组数据说明：1.5B 的能力是够的，前提是 prompt 必须按中文语境精心设计。** 想直接丢个英文 schema 过去，准确率会腰斩。

## 三、设备的硬约束（实测）

| 项 | 实测值 | 对端侧 LLM 的影响 |
|---|---|---|
| SoC | 天玑 6833（A76×2@2.4G + A55×6） | 无强 NPU，只能 CPU 推理，**慢** |
| 内存 | 7.7 G 总 / **2.6 G 可用**，已在用 swap | 1.5B Q4 常驻约 1.2~1.8 G，**会挤爆** |
| 存储 | /data **仅剩 1.8 G**（99% 满） | 塞 1 GB 模型进去**几乎不可能** |
| ABI | arm64-v8a | ✓ 支持 |
| GMS | 有，但**无 AICore** | ✗ Gemini Nano 路线排除 |

这两条硬约束是致命的：

1. **存储不够**：1.5B Q4 模型 1066 MB，塞进 APK 后总包约 1.1 GB。设备只剩 1.8 G，装完就剩 0.7 G——用户大概率装不上。
2. **内存不够**：MemAvailable 2.6 G，且 swap 已用 3 G。加载 1.5B + 系统常驻，MIUI 的 LMK 会**优先杀掉后台的无障碍服务**——这直接摧毁自动记账本身。

**速度估算**：天玑 6833 的 A76 单核约为 PC i5-14400F 的 25~30%。PC 上这 8 个案例（平均输出 42 token）耗时约数秒/例，换算到手机大约：

- 输入 300 token + 输出 40 token
- 预计 **3~8 秒/次**

记账场景可接受（不是实时交互），但**每次要占 1.5 G 内存 3~8 秒**，对一台 2.6 G 可用的机器是很重的负担。

## 四、可行性判定

### 4.1 三条路，逐条判

| 方案 | 可行性 | 理由 |
|---|---|---|
| **打包进 APK 当主力** | ✗ **不可行** | 包体 1.1 G + 存储只剩 1.8 G；常驻内存会挤掉无障碍服务 |
| **首次启动按需下载模型** | △ **勉强** | 绕开 APK 体积，但 1 GB 下载 + 1.8 G 存储，用户体验差 |
| **规则为主 + 1.5B 兜底** | ✓ **推荐** | 只在规则不确定时调用，绝大部分账单走规则（0 成本 0 延迟） |

### 4.2 推荐方案的工程形态

```
┌─ 账单文本进来
│
├─ 1. 规则/模板解析（现有 BillParser）          0 ms，0 内存
│     置信度 >= 80 → 直接入账                    ← 覆盖约 80~90% 账单
│
├─ 2. 规则不确定（50~79 或商户为空）
│     → 调 1.5B 本地推理补商户/校验金额          3~8 s，1.5 G
│     修好了 → 入账
│
└─ 3. 仍不确定 / 模型加载失败 / 内存不足
      → 进待确认队列，等用户一键确认
```

**关键设计**：

- 模型**不打包进 APK**，设置页提供「下载离线解析模型（1.1 GB）」按钮
- 模型只在**用户开启**且**屏幕亮着**（前台充电时）才加载，用完立即释放
- 加载前检查 `MemAvailable`，低于 3 G 直接跳过，退回待确认队列
- 失败绝不阻塞记账主流程

### 4.3 性价比判断

说句实话：**就这台设备而言，1.5B 兜底的收益不太划算。**

- 它能补的是「商户名」，而规则错商户的 3 个案例（京东→名称、招商→短信、红包→微信）**都可以用规则修**——加几条标签映射就完事，成本近乎零
- 代价是 1.1 GB 存储 + 1.5 G 内存峰值 + 3~8 秒延迟 + 潜在的服务被杀风险

**投入产出比排序**：

1. 修那 3 个商户规则缺陷 —— 半小时，直接 5/8 → 8/8
2. 接 `NotificationListenerService` —— 数据源质变
3. 待确认队列
4. 端侧 1.5B 兜底 —— **最后考虑**

## 五、如果坚持要走端侧 LLM

给几条能省一半力的建议：

1. **别用 Qwen2.5-1.5B 的通用对话版**，用**专门做信息抽取的模型**或对它做少量微调。通用对话模型在结构化抽取上浪费了大量参数在「聊天能力」上。
2. **prompt 必须是中文枚举 + few-shot**（实测 38% → 88%，这一条价值最大）。
3. **用 Q4_K_M 而非 Q8**——1.5B 的 Q4 质量损失在抽取任务上很小，但体积从 1.8 G 降到 1.07 G。
4. **限制输出长度**（`max_tokens=128`）。实测平均只需 42 token，给多了它反而容易自我重复（0.5B 那次就重复输出了 amount 字段）。
5. **必须做 JSON 容错解析**——实测 1/8 概率输出带 markdown 包裹或数组而非对象。
6. **推理引擎选 llama.cpp（JNI）或 MLC-LLM**，别自己造。
