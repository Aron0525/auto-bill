# 现状诊断：OCR 与自动记账

诊断时间：2026-11-12 · 设备：小米 2312DRAABC / Android 14 · 版本 1.5 (5)

本文档只写**实测证据**，不写推测。所有结论可在文末「复现方法」重新验证。

---

## 一、最重要的一个发现：OCR 根本不在自动记账链路上

这是理解全部问题的前提。

代码里两条链路**完全独立、没有任何交集**：

| 链路 | 入口 | 技术 | 触发方式 |
|---|---|---|---|
| **自动记账** | `AutoBillAccessibilityService` | 无障碍读取 `AccessibilityNodeInfo` 文本 | 被动，App 自己来找 |
| **手动识图** | `MainActivity.pickImage` / `ShareActivity` / `AddBillActivity` | ML Kit OCR | 主动，用户点「识图」 |

验证方式：在 `AutoBillAccessibilityService.java` 里搜索 `OcrHelper`、`OcrTemplates`、`recognize`、`parseOcr` —— **零匹配**。

**推论**：截图 OCR 再差，也不会让自动记账变差；反之亦然。之前「OCR 识别能力弱 + 自动记账效果差」这两句，实际是两个独立问题被合并成了一个印象。

它们的共同点是：**都基于「先把文本压平，再用正则去猜」这个错误架构**，所以症状相似——但药方不同。

---

## 二、账本实测：66 条里只有 1 条是真机抓的

从设备拉取 `autobill.db` 逐条核对（方法见文末）：

```
表: bills  66 行
```

原文分布：

| raw 原文 | 条数 | 性质 |
|---|---|---|
| `微信支付 消费` | 53 | 演示数据（dedup 键为 `demo1`/`demo2`…） |
| `工资到账` | 12 | 演示数据 |
| 216 字的整屏通知栏 | **1** | **真机唯一一条，且是错的** |

演示数据来源已确认：`work_tmp\gen_db.py` 脚本，`random.seed(7)` 生成 2025-12 ~ 2026-11 共 12 个月的假账单，`dedup` 键为 `demo1`/`demo2`…/`demo_inc1`…。**这些不是 App 抓的。**

也就是说：**「自动记账效果很差」这个判断，依据的其实是演示数据，不是真实抓取结果。** 真机自动记账在这台设备上几乎没有实际运行过（原因见第四节）。

### 唯一一条真机记录错在哪

```
_id       = 66
platform  = com.android.systemui       ← 来源是「通知栏」，不是微信/支付宝
raw       = 17:14 设置 11月10日 周二 手机可用空间不足3G 展开 Shell 收起
            支付宝 基金申购确认成功通知 12:37 你于2026-11-06买入易方达
            中债3-5年期国债基金已确认成功，确认金额99.92元，手续费0.10元
            ... 已连接到 USB 调试 ... 热点已启用 ... 历史通知 清除所有通知

merchant   = 通知栏        ← 商户名成了「通知栏」
amount_fen = 9992          ← 99.92 元，但它其实是「申购确认金额」
note       = 手续费        ← 把 0.10 元手续费当成了备注
category   = 投资/理财
confidence = 65
```

**四个字段错三个**，根因是把「整屏通知列表」当成了一个文本源：

1. **系统噪声混入**：`手机可用空间不足3G`、`已连接 USB 调试`、`热点已启用` 全是系统通知
2. **多通知粘连**：整个列表被 `collectText` 递归拼成 216 字的一段
3. **金额归属错误**：原文里有两个金额（99.92 申购额 / 0.10 手续费），规则抓了大的那个，但语义上这笔的主体是「申购」，备注却取了「手续费」
4. **商户兜底丑陋**：取不到商户就用来源名填 `通知栏`

好消息：当前代码里 `SYSTEM_UI_PKGS` 已经把 `com.android.systemui` 拉黑（第 78-83 行），并写明了原因注释。**这条数据是修复前的遗留**，现在不会再犯。坏消息：拉黑只是「不记错」，代价是「也记不到」——这才是自动记账效果差的真正原因。

## 三、OCR 实测：能认字，但不会「看版式」

三张真机截图（美团 / 微信 / 支付宝）复测结果，修复后金额全对：

| 图 | 金额 | 商户 | 置信 |
|---|---|---|---|
| 美团（7 个干扰金额） | 39.20 ✓ | 华莱士炸鸡汉堡(科技园店) ✓ | 55 |
| 微信支付 | 128.50 ✓ | 星巴克咖啡(万象城店) ✓ | 92 |
| 支付宝（金额换行） | 56.80 ✓ | 麦当劳(软件园店) ✓ | 75 |

但这三张是**合成图**——干净、无遮挡、标准字体、我自己排的版式。真实截图的难度高一个量级：

| 真实场景的难点 | 当前能否处理 |
|---|---|
| ML Kit 返回顺序不是视觉顺序（标签一列、数字一列） | 已用包围盒排序解决 |
| 异体字（商家实测把「额」认成「颉」、「户」认成「戶」） | 已建映射表，但只能穷举见过的 |
| 金额与标签跨行（「支付金额」下一行才是「56.80」） | 已处理 |
| 弹窗遮挡 / 半透明蒙层 / 深色模式 | **不能** |
| 红包、优惠券、积分抵扣同时出现多个金额 | **勉强**，靠标签强弱 |
| 字体极小（<12sp）或数字粘连 | **不能** |
| 非标准版式（小众 App、网页、小程序） | **不能**，退回通用规则瞎猜 |

**结论**：OCR 的字识别率（ML Kit 中文模型）本身不差，约 95%+。真正差的是**「从一堆文字里判断哪笔是哪笔」的版式理解能力**。这不是换 OCR 引擎能解决的——换 PaddleOCR 或云端 OCR，认字率提升有限，版式理解依然是零。

### 架构上的根本缺陷

现在是 **「OCR → 压平成一串文本 → 正则猜金额」**。文本一旦压平，位置、对齐、分组信息全部丢失，之后所有补救（模板、强弱标签、跨行）都是在把丢掉的信息重新猜回来。

**正确做法是反过来：先保住结构，再在结构上做定位。** ML Kit 本来就给了 `BoundingBox`，我们只用它排了个序就扔掉了——这是最大的浪费。

## 四、自动记账实测：三条通道，两条不成立

当前实现依赖三个来源，逐个核对：

### 通道 A：无障碍通知事件 —— 技术上可用，但很脆

```java
if (type == AccessibilityEvent.TYPE_NOTIFICATION_STATE_CHANGED) {
    if (!TARGET_PKGS.contains(pkg)) return;
    handleNotification(event, pkg);
}
```

问题：

- 依赖 `event.getParcelableData()` 拿 `Notification`，在 MIUI 上**经常为 null**，退化到 `event.getText()`，只能拿到标题级的短文本
- 微信支付通知本身就不含商户名（只有「微信支付」「已支付¥xx.xx」），**光靠通知拿不到商户**——这是产品设计，不是 bug
- MIUI 对后台应用有「省电策略」，服务被杀后**不会自动重启**

### 通道 B：无障碍屏幕文本 —— 主力，但被过度收紧

`handleWindow` 只对 `TARGET_PKGS` 生效。这台设备上实际安装情况：

| App | 模板 | 装了吗 |
|---|---|---|
| 微信 | ✓ | ✓ |
| 支付宝 | ✓ | ✓ |
| 美团 | ✓ | ✓ |
| 淘宝 | ✓ | **✗ 未安装** |
| 京东 | 无模板 | **✗ 未安装** |
| 拼多多 | 无模板 | **✗ 未安装** |

**5 个模板里 2 个在这台设备上永远触发不到。** 写了用不上的代码。

而且 `TARGET_PKGS` 是硬编码白名单——用户装了新 App 就要改代码重新发版。策略上是错的。

### 通道 C：NotificationListenerService —— **根本没用**

```bash
$ adb shell settings get secure enabled_notification_listeners
com.xiaomi.barrage/...:com.huawei.health/...
```

没有 `com.aron.autobill`。App 也**没有实现** `NotificationListenerService`（Manifest 里只有 AccessibilityService）。

这是最大的技术损失。`NotificationListenerService` 相比无障碍通知事件的优势：

| 能力 | 无障碍通知事件 | NotificationListenerService |
|---|---|---|
| 拿到完整 `Notification` 对象 | 经常为 null | **总是有** |
| 拿到 `EXTRA_BIG_TEXT` 全文 | 常被截断 | **完整** |
| 拿到通知历史 | ✗ | ✓ `getActiveNotifications()` |
| 拿到应用名/图标 | ✗ | ✓ |
| MIUI 稳定性 | 差 | **好得多** |
| 系统标准 API | 非本职 | **正是本职** |
| 审核风险 | 无障碍被严查 | **低** |

**结论：自动记账效果差的主因不是解析规则不够聪明，而是「数据源没接对」。** 用错 API 拿残缺数据，再聪明的正则也救不回来。

### 通道 D：屏幕截图 + OCR —— 完全没接

当前 OCR 只在用户手动点「识图」时跑。**自动记账链路里没有截图能力**：需要在 Service 里调 `MediaProjection` 截屏 + OCR，技术可行但代价大（常驻录屏权限、耗电、隐私顾虑）。这是最后手段，不该是主路径。

## 五、三个问题的因果链

```
自动记账效果差
├── 主因 1：数据源用错 API（无障碍通知事件 → 应为 NotificationListenerService）
│            → 拿不到完整正文、拿不到商户、MIUI 上经常失效
├── 主因 2：只覆盖 3 个已安装 App，且白名单硬编码
│            → 用户装新 App 就漏
├── 主因 3：拿到文本后「压平再正则猜」，丢失结构
│            → 遇到没见过的版式必错
└── 次因：MIUI 省电策略杀服务，用户不知道要手动保活

OCR 识别能力弱
├── 主因：只做「认字」，不做「版式理解」，压平后位置信息全丢
├── 次因：模板只覆盖 5 个 App，且是硬编码字符串匹配
└── 次因：只出 1 个答案，错了用户也不知道该改哪
            （虽然已有候选对话框，但候选质量差——都是「全图扫金额」的结果）

两者共同根因
└── 架构：把有结构的信息压平成文本，再用字符串规则猜
    药方不是「换个更强的 OCR」或「加更多正则」，
    而是「保住结构 + 接对数据源 + 让用户确认兜底」
```

## 复现方法

```powershell
$adb = "E:\codex\2026-10-25\new-chat\work\android-tools\platform-tools\adb.exe"
$dev = "8xmzgyi7u45tgi7t"

# 1. 拉账本（必须用 exec-out + cmd 重定向，PowerShell 的 > 会写成 UTF-16 损坏文件）
cmd /c "`"$adb`" -s $dev exec-out `"run-as com.aron.autobill cat databases/autobill.db`" > E:\DSH\REA\work_tmp\ab.db 2>nul"

# 2. 确认 OCR 不在自动记账链路
#    在 AutoBillAccessibilityService.java 里搜 OcrHelper / parseOcr → 零匹配

# 3. 确认通知监听服务没接
& $adb -s $dev shell settings get secure enabled_notification_listeners

# 4. 确认目标 App 安装情况
foreach($p in @("com.tencent.mm","com.eg.android.AlipayGphone","com.sankuai.meituan","com.taobao.taobao")){
  $r = (& $adb -s $dev shell pm list packages $p).Trim()
  "{0,-32} {1}" -f $p, $(if($r){"已安装"}else{"未安装"})
}

# 5. 无障碍服务是否健康（Crashed services 非空 = 事件全收不到）
& $adb -s $dev shell dumpsys accessibility | Select-String "Crashed services"
```
