# 消息处理精准度提升

分两轮做。第一轮改解析逻辑，第二轮换成**用户真机实际安装的 App** 出题。

验收方式：`NotifPrecisionSelftest` 考卷从 0 涨到 37 题，按真实通知字段结构出题。
最终 37/37，且原有断言零退化（全套 **245 条全绿**）。

---

## 一、第一轮：字段结构被丢了（v1.7）

真机 `dumpsys notification --noredact` 抓到的真实结构：

```
android.title    = "微信支付"
android.text     = "支付成功 ¥128.50 收款方：星巴克"
```

**title 常常是 App 名，text 才是交易详情。**

旧实现把所有字段拼成一个字符串：

```java
sb.append(title).append(' ');      // ← 问题在这里
sb.append(bigText != null ? bigText : text);
```

于是 `"微信支付" + "支付成功 ¥128.50 收款方：星巴克"` 变成一段文本，
解析器从前往后找商户，第一个像店名的就是「**微信**」。

这不是规则没写对，是**信息在进入解析器之前就被搅混了**。

### 1.1 新增 `parseNotification`

```java
ParseResult parseNotification(String title, String text, String bigText, String pkg);
```

核心是**标题不当正文用**：

1. 正文单独解析（bigText 优先）→ 拿到干净结果
2. 标题只在正文没给出商户时才作候选，且必须通过合理性校验
3. 标题是银行名时例外——账单通知里银行就是商户
4. 标题里没有方向词而正文也没有时，用标题补方向

配套 `isAppNameLike()` 判定标题性质、`extractBankNameFromTitle()` 剥卡种后缀。

### 1.2 金额择优 `pickAmount`

金额记错比商户记错严重得多——账本直接失真。旧实现返回**第一个**匹配：

| 文本 | 旧结果 | 正确 |
|---|---|---|
| 商品小计 47.20 配送费 4.00 优惠 -8.00 **实付 39.20** | 47.20 | 39.20 |
| 商品总价 599.00 优惠券 -100.00 **实付款 499.00** | 未解析 | 499.00 |
| 赎回金额 5000.00 手续费 5.00 **实际到账 4995.00** | 5000.00 | 4995.00 |

新实现收集**所有**候选，逐个打分：

| 层级 | 词 | 分 |
|---|---|---|
| 最高 | 实付 / 实际到账 / 实收 | 130 |
| 高 | 应付 / 合计 / 支付 / 到账 / 消费 | 100 |
| 低 | 小计 / 配送费 / 优惠 / 手续费 / 余额 / 赎回金额 | 15 |

关键细节：

- **只认紧贴金额前 6 字内的标签**。一开始用 ±14 字窗口，
  「配送费 4.00 优惠 -8.00 实付」里 `4.00` 也吃到了「实付」，评成了最高分。
- **候选必须有货币证据**（`¥`/`元` 或紧邻交易标签），否则银行卡尾号 `1234`、
  客服电话 `95588` 会被当成金额。
- **负号金额**（`优惠 -100.00`）过滤掉。

### 1.3 商户：`entityAfterAmount`

真实通知常见排版是「标签 金额 商户名」：

```
「实付 39.20 华莱士」          → 华莱士
「支付成功 ¥128.50 星巴克咖啡」 → 星巴克咖啡
```

排在**商户词表之前**。旧逻辑先命中 `MERCHANT_HINTS` 里的「饿了么」，
而真实商户「华莱士」排在句末根本轮不到——平台名压过真实店名是另一大错账来源。

### 1.4 三个隐蔽的拦截误伤

**「优惠券」不该无条件拦**

```
「订单支付成功 商品总价 599.00 优惠券 -100.00 实付款 499.00 优衣库」
```

这是真实订单，却因含「优惠券」被整条丢掉。改为上下文判定，
只有「领券/抢券/送券/券过期」才拦。

**「送红包」≠「发送红包」**

第一次修上方问题时写得太宽，把「你已**发送红包** ¥88.00」也拦了，
规则基线从 8/8 掉到 7/8。改为 `(?<!发|寄|投)(?:送)`。

**「共2笔交易」的 2 不是金额**

`maskNonAmount` 补了计数词：`共N笔` `N笔交易` `剩余N期` `第N期` `分N期`。

### 1.5 异体字归一提前

`normalize()` 第一步就调 `OcrTemplates.norm()`：

```
「商戶全称 星巴克 支付金颉 128.50 余額宝」
旧：商户 = 余額宝（「余额宝」没认出来，渠道词过滤失效）
新：商户 = 星巴克
```

## 二、第二轮：用真机实际安装的 App 出题（v1.8）

第一轮改完后，我把考卷扩充到**用户真机实际安装的 App**。
做法是 `pm list packages -3` 拉出全部包名，挑出会推交易通知的，
逐个造样本跑诊断——一次性暴露了 **10 处错账**，全是第一轮没覆盖的。

**教训：用没装的 App 出题，等于在测空气。**
淘宝/京东/饿了么都没装；真正天天推通知的是三大运营商、建行、中行、
美团、高德、小米钱包、12306。

### 2.1 包名直接进了账本

```
商户 = com.greenpoint.android.mc10086.activity
商户 = com.mipay.wallet
```

`platformName()` 原来是 `getOrDefault(pkg, pkg)`——未收录的包名**原样返回**，
而 `detectMerchant()` 最后一步就是拿它兜底。

修法两条：

- 补齐 30+ 真实包名映射（三大运营商、建行、中行、美团、高德、小米钱包、12306…）
- 未收录包名一律返回「其他」，绝不原样吐出

另加 `isPackageLike()` 兜底：任何 `com.xxx.yyy` 形态的字符串都不能当商户名。

### 2.2 标题是 App 名，不等于标题没用

**只有真机才暴露**的问题。用 `cmd notification post` 发通知时，
`pkg` 是 `com.android.shell`，`platformName()` 只能返回「其他」；
正文「您已使用小米公交卡刷卡，扣款5.00元」里也没有商户——两边都给不出。

但标题明明写着「小米钱包」。

旧逻辑 `if (!titleIsAppName) { ...用标题兜底... }` 把「App 名」和「不能用」划了等号。
实际上要分开看：

| 场景 | 该不该用标题 |
|---|---|
| 正文有真实商户（瑞幸咖啡） | **不行**，App 名不能压过真实商户 |
| 正文给不出商户 | **应该**，App 名就是用户看到的商户 |

改成：`titleIsAppName` 时**只在正文无商户时**用 `platformName(pkg)` 兜底，
pkg 也认不出就退回标题本身。兜底可信度不升反降 5 分。

### 2.3 余额宝收益被判成支出

```
「余额宝昨日收益0.52元，累计收益128.30元」→ 支出 ¥0.52
```

`detectType()` 本身算对了（返回 2 = 收入），是 `parseNotification` 把它覆盖了：
正文没有方向词时用**标题**定方向，而标题「支付宝」含「支付」，被判成支出。

标题只是兜底线索，不该有权推翻正文的结论。改成：

- 标题是 App 名时，一律不参与定方向
- 标题必须含**明确的方向词**（收款/退款/到账/收益）才能采信

### 2.4 「还没发生的钱」被当成已支出

这一类最危险，它会**凭空多出支出**，还会在真扣款时再记一笔：

| 通知 | 旧行为 | 问题 |
|---|---|---|
| 话费已欠费12.30元 | 记 ¥12.30 支出 | 用户还没交钱 |
| 花呗本月账单1280元 | 记 ¥1280 支出 | 这是待还，不是已还 |
| 打车预估26元 | 记 ¥26 支出 | 真扣 31 元时再记一笔 |

新增 `EXPENSE_FUTURE` 正则识别这类语境，命中则置信度 **-60**。

扣这么多是必要的：这类文本动作词齐全（「已欠费」「还款日」），
基础分本就能堆到 50+，扣 40 仍会卡在自动入账线上。

结果它们进**待确认队列**，不直接入账——既不污染账本，用户也能在队列里看到。

### 2.5 动作词被当商户名

```
「退款18.60元已原路退回」→ 商户「已原路退回」
「车费32.50元已自动支付」→ 商户「已自动支付」
「退款将原路退回」      → 商户「将原路退回」
```

新增 `ENTITY_BAD_CONTENT`（原路退回/自动支付/请注意查收…）
和 `ENTITY_BAD_LEAD`（以「已/将/会/正在/请/共/合」开头的候选）。

### 2.6 公交卡 ≠ 小米之家

```
「您已使用小米公交卡刷卡，扣款2.00元」→ 商户「小米之家」
```

`MERCHANT_HINTS` 里有 `{"小米", "小米之家"}`，用 `contains` 匹配——
「小米公交卡」含「小米」就被配成了小米之家，用户根本没去过。

修法：

- 品牌词移到 `MERCHANT_EXACT` 表，必须**精确**出现才认
- 加 `cardContext` 判定：文本含「公交卡/交通卡/钱包/账户」时品牌词不当商户

### 2.7 分类：具体场景必须压过平台王牌

顺序即优先级。原来 `order = {餐饮, 购物, 交通, ...}`，而「餐饮」词表里有「美团」：

```
「美团打车 行程已结束，本次支付18.60元」→ 分类「餐饮」
```

改成 `{交通, 医疗, 娱乐, 生活缴费, 通讯, 餐饮, 购物}`，
并把「美团」从餐饮词表换成更具体的「美团外卖」「美团买菜」。

银行消费提醒通常不带品类词，兜底从「其他」改成「购物」——
用户看账本时至少能按消费聚合。

## 三、一个真实的 Java 陷阱

```java
Long fen = cand != null ? cand.fen : extractAmount(masked);
```

`cand.fen` 是 `long`、`extractAmount` 返回 `Long`，三元运算符按 JLS 会做
**二元数值提升**，把 `Long` 强制拆箱——`extractAmount` 返回 `null` 时直接 NPE。
`CandidateSelftest` 抓住了它。改成分开写的 if/else。

## 六、还没解决的

1. **微信一对一转账卡片**：通知里可能只有「[转账]」两个字，金额要进 App 才看得到，
   只能靠 OCR 兜底。
2. **同一笔多通道重复**：通知 + 无障碍 + OCR 三条路都可能看到同一笔，
   现在靠 5 分钟窗口 + `findSimilar`，跨更长时间（如退款隔天到账）仍会重复。
3. **打车行程结束才扣费**：预估那条现在会进待确认队列，
   但用户如果手动确认了，真扣款时还是会再记一笔。
4. **运营商/银行的推送格式经常变**：这轮样本是按现有格式造的，
   换季改版后可能失配。需要靠待确认队列兜住。
