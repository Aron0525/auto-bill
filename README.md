# AutoBill · 自动记账

一个**纯本地**的 Android 自动记账 App：从微信 / 支付宝的交易通知里识别金额、商户、分类，自动记进本机账本。不联网、不上传、不依赖任何云服务。

> 因为市面上能做到「不联网还能自动记账」的 App 基本没有 —— 大部分都要上传账单做云端解析。这个项目就是为了不把自己的消费记录交出去。

---

## 它解决什么问题

手动记账最难的不是记账，是**坚持**。所以核心思路是：

> 你付完钱，手机本来就会弹一条「微信支付 支付成功 188.50 元 收款方：星巴克咖啡」。
> 这条通知已经包含了记账需要的全部信息 —— 为什么要让你再手动录一遍？

AutoBill 常驻通知监听，把这类通知解析成结构化账单：

| 输入（通知原文） | 解析结果 |
|---|---|
| `微信支付 支付成功 188.50 元 收款方：星巴克咖啡 支付方式：零钱` | 支出 ¥188.50 / 星巴克咖啡 / 餐饮 / 置信度 95 |
| `支付宝 付款成功 56.80 元 付款给 麦当劳` | 支出 ¥56.80 / 麦当劳 / 餐饮 / 置信度 90 |

## 三个设计原则

### 1. 宁可不可，不可错记

金额记错比漏记严重得多 —— 漏记你只是少一条，记错了整个账本就不可信了。

所以拿不准的交易**不进账本，进「待确认」队列**，让你一眼扫过去点确认。不静默丢弃，也不猜着记。

### 2. 数据不出本机

- 账本是本机 SQLite
- 截图 OCR 用 ML Kit 自带模型，本地推理
- 唯一的联网行为是「检查更新」（可关闭，地址由你配置）

### 3. 不用第三方 UI 库

只用 AndroidX + Material Components，没有 Compose、没有第三方图表库、没有网络框架。整个 App 45 MB，其中 40 MB 是 ML Kit 的中文 OCR 模型。

## 架构：两条采集通道

```
┌─────────────────────────────────────────────────────────────┐
│  通知通道（主）                                              │
│  NotificationListenerService                                │
│    ↓ 拿 Notification.extras 完整正文                        │
│    ↓ NotifPolicy：按渠道 ID 分流（营销/订阅/物流直接丢）    │
│    ↓ 去重五层（身份/指纹/节流/DB相似/唯一索引）             │
├─────────────────────────────────────────────────────────────┤
│  读屏通道（辅）                                              │
│  AccessibilityService                                       │
│    ↓ 抓当前屏幕可见文本（800ms 节流）                        │
│    ↓ ScreenPolicy：应用级开关 + 浏览页识别 + 结账凭证门禁    │
├─────────────────────────────────────────────────────────────┤
│  BillParser：金额分级 → 商户定位 → 分类 → 置信度             │
│    ↓                                                        │
│  置信度 ≥50 → 账本    <50 → 待确认队列                       │
└─────────────────────────────────────────────────────────────┘
```

### 为什么需要两条通道

两条通道都建立在一个前提上：**进程活着、监听连着**。这一层失效时，上面所有解析规则都不会被触发，账本一条也不会多 —— 见下一节「稳定性」。

| 能力 | 通知通道 | 读屏通道 |
|---|---|---|
| 通知对象完整 | ✓ | ✗（常为 null）|
| 能读到余额、订单号 | ✗ | ✓ |
| 小程序内付款 | 部分 | ✓ |
| **商品浏览页会不会误记** | ✗（不会有假账）| **会 —— 必须严格过滤** |

**读屏是假账的重灾区。** 商品列表页满屏「¥9.9」，每滑一屏就可能多一条账单。这一块的方案见 [应用读屏权限](docs/应用读屏权限.md)。

---

## 稳定性：付了钱为什么没记账

解析准不准是第二位的。第一位是**服务到底在不在岗**，而这一层出问题时，用户看到的现象和「没花钱」一模一样。

四道保证，缺一不可：

| 机制 | 解决什么 | 代码 |
|---|---|---|
| 前台服务 + 常驻无声通知 | MIUI 回收进程后监听不会自己复活 | `KeepAliveService` |
| 开机自启 + 每 5 分钟自检重绑 | 重启后静默失效、运行中掉线 | `BootReceiver` / `NotifBinder` |
| 重连时补捞通知栏 | 断线期间的通知不会补发事件 | `getActiveNotifications()` |
| 状态行 + 常驻通知计数 | 用户能自己判断「有没有在收」 | 主页 / 设置页 |

常驻通知的文案会跟着状态变：`通知使用权未开启` → `监听未连接，正在尝试恢复` → `已接收 N 条交易通知`。付了钱但数字不动，当场就能发现，不用等一周才发现账本缺了一截。

## 难点与解法

### 商品浏览页 vs 结账成功页

这是最棘手的问题。两者都有一堆金额，但一个是「展示价格」，一个是「真实交易」。

解法是**三层门禁**：

1. **应用级开关** —— 用户可把任何 App 设为「不读屏」
2. **商品页特征识别** —— 出现「加入购物车 / 立即购买 / 去结算」直接放弃
3. **结账凭证要求** —— 必须命中「支付成功 / 实付款 / 支付方式 / 订单编号」

详见 [应用读屏权限](docs/应用读屏权限.md)。

### 群聊消息里的「张三: 已转账 200 元」

微信群里别人转账给你，通知标题是群名。曾经把它记成商户「工作群」直接入账。

解法：识别「发送者: 内容」结构（冒号在前 16 字符内、左侧 ≤12 字、且不含数字和金额符号），判定为聊天消息 → 压到待确认。

反例保护：`收款方：星巴克` 也有冒号，但左边是标签不是人名，不能误判。

### 微信转账/红包拿不到金额

微信的转账卡片通知里**只有「[转账]」，没有金额** —— 这是微信自己的产品设计，任何读取通知的方案都拿不到。

诚实结论：
- **消费支付** → 高精度自动记账 ✓
- **转账 / 红包** → 只能检测到「有一笔」，弹「待补全」提示让你点进去看 ✗

详见 [消息精准度](docs/消息精准度.md)。

### 通知去重

同一条通知会重复投递（更新进度、亮屏、展开通知）。五层去重：

1. 通知身份 `pkg:id:when`（30 分钟窗口）
2. 正文指纹
3. 800ms 节流
4. DB 相似查询（5 分钟）
5. `dedup UNIQUE + CONFLICT_IGNORE`

详见 [通知去重机制](docs/通知去重机制.md)。

## 测试：497 条断言

项目没有用 JUnit / Espresso，而是**纯 JVM 自检**（`java` 直接跑，无 Android 依赖）：

```bash
bash selftest/run.sh          # 全部跑一遍，含编译
bash selftest/run.sh Parser   # 只跑类名含 Parser 的
```

脚本固定了编译范围、类名（多数自检在 `com.aron.autobill.selftest` 包下，直接写简名会 ClassNotFoundException）与统计口径，输出形如 `合计：通过 497 / 失败 0`，非零退出即代表有用例失败。

| 自检 | 断言数 | 覆盖 |
|---|---|---|
| `ParserSelftest` | 51 | 金额/商户/分类/方向基础用例、标签词边界 |
| `OcrSelftest` | 19 | OCR 文本行还原 |
| `TemplateSelftest` | 31 | 5 个 App 的版式模板 |
| `RealImageSelftest` | 11 | 真实截图端到端 |
| `UpdateSelftest` | 61 | 更新协议、哈希、魔数、取消、响应上限 |
| `GithubUpdateSelftest` | 85 | GitHub 通道、地址归一、版本量纲、断点续传 |
| `UpdateHttpSelftest` | 15 | 真 HTTP：200/206/416/302/404、服务器不认 Range |
| `NotifPrecisionSelftest` | 37 | 通知解析精度 |
| `ChannelPolicySelftest` | 30 | 渠道分流策略 |
| `NotifPipelineSelftest` | 14 | 策略 → 解析器接缝、置信度门槛 |
| `NotifLogSelftest` | 41 | 通知留痕（在岗证据） |
| `ScreenPolicySelftest` | 27 | **浏览页 vs 结账页** |
| `VisualSortSelftest` | 33 | 图表排序 |
| 其余 | 42 | 分类、通知切割、多候选、模型基线 |
| **合计** | **497** | **0 失败** |

**为什么不用标准测试框架**：解析器的核心逻辑是纯字符串处理，不需要 Android 运行时。纯 JVM 自检跑一次只要几秒，做一次改动能立刻验证全部 497 条，这个反馈速度是 Instrumentation 测试给不了的。

## 构建

**要求**：JDK 17、Android SDK 34

```bash
# 1. 创建 local.properties
echo "sdk.dir=/path/to/Android/Sdk" > local.properties

# 2. 构建
./gradlew assembleDebug
```

产物在 `app/build/outputs/apk/debug/app-debug.apk`。

## 安装后必做

1. **开启通知使用权** —— 设置 → 通知使用权（这是主通道，不开等于没用）
2. **允许通知** —— Android 13+ 会弹一次申请；拒绝的话记账横幅和常驻通知都看不见
3. **开启无障碍服务** —— 设置 → 无障碍 → 自动记账（这是辅助通道）
4. **MIUI / HyperOS 额外设置**：
   - 应用设置 → 省电策略 → **无限制**
   - 应用设置 → 自启动 → **允许**（开机自启靠它，否则重启后静默失效）
   - 最近任务里给 App **加锁**（防止清理时被杀）

前两项如果不做，MIUI 会拒绝启动无障碍服务。

装好之后通知栏会常驻一条**无声**的「自动记账运行中」，文案会显示当前状态。不要清掉它，也不要关掉这个渠道 —— 它就是保活服务本身，关掉等于让监听重新变成随时会被回收的普通进程。

主页顶部有两行状态：通知监听（主通道）和无障碍（辅助通道）。付了钱没记账时先看第一行，它会告诉你卡在「未授权」「未连接」还是「正常但没收到」。

## 隐私

- 所有数据仅存本机 SQLite，无云端
- 截图识别用 ML Kit 自带模型，本地推理，不上传图片
- 无障碍权限仅用于读取支付相关通知与页面文字
- 「检查更新」是唯一联网入口，可关闭

## 已知限制

| 限制 | 原因 | 能否解决 |
|---|---|---|
| 微信转账/红包无金额 | 通知里就没有 | ✗ 产品设计决定 |
| 短信通道未实现 | 需要 `RECEIVE_SMS` 权限 | 可做，优先级低 |
| 部分银行 App 需手动 | 各银行通知格式不同 | 可加模板 |
| 商品页仍可能漏判 | 特征词有限 | 持续补规则 |
| 杀掉进程期间的支付可能丢 | 系统不补发通知事件 | 部分解决：重连时补捞通知栏，用户若已划掉通知则捞不到 |
| MIUI「自启动」关着时开机不自启 | 系统不投递 `BOOT_COMPLETED` | ✗ 只能靠用户打开 App 兜底，设置页有引导 |
| 群聊里「张三: 已转账 200元」 | 聊天内容不是真实交易 | 压到待确认队列，不直接入账 |
